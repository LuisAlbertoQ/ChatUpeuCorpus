POR QUE SE BLOQUEABA ANTES (el M06 con 30s o 47s):

  1. PROMPT ENORME
     5 chunks x ~2000 chars = ~10000 chars = ~2500 tokens de contexto
     + 800 tokens de prompt + 512 tokens de respuesta
     = 3800+ tokens -> n_ctx=4096 -> muy justo

  2. OFFLOAD GPU<->CPU
     Tu log decia: "offloaded 30/33 layers to GPU"
     3 capas quedan en CPU, se intercambian con cada inferencia
     Picos de 20-40s en lugar de 5-10s

  3. LOOP INTERNO DEL LLM
     Si el prompt esta en el limite, el modelo puede entrar en loop
     generando el mismo token repetido -> no termina nunca
     Ollama devuelve HTTP 500 despues de 15s de timeout interno

  4. SIN BACKOFF
     Antes: 2 intentos sin espera -> si Ollama estaba sobrecargado,
     ambos intentos fallaban rapidamente -> M06

AHORA:
  - UMBRAL 0.32 -> 0.35: captura el chunk correcto
  - TIMEOUT 15s -> 25s: da margen a Ollama con offload
  - Recorte 1200 chars: evita prompts > 3000 tokens
  - 3 reintentos con backoff: tolera HTTP 500 transitorio
  - docker-compose restart backend: aplica cambios de codigo

EL FRONTEND NO BLOQUEA EL SISTEMA:
  - Solo deshabilita el boton "Enviar" mientras `cargando=true`
  - Si quieres cancelar, solo cierra la pestana o navega
  - El backend tiene 3 reintentos maximos (techo ~77s)
  - Despues de eso, devuelve M06 honestamente

EL BACKEND SI BLOQUEA EL REQUEST HTTP:
  - uvicorn es sync (no async)
  - El handler espera la respuesta del LLM
  - Si el LLM tarda, el request HTTP espera
  - Frontend muestra spinner hasta respuesta o error
