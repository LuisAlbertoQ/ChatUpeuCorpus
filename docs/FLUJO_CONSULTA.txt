+--------------------+   (3) rag_pipeline.py
| RAG PIPELINE       |
|                    |
| (a) Validaciones:  |   - ambigua (M05), etica (M03), multi-intencion (M05),
|                    |     fuera-dominio keywords (M03)
|                    |
| (b) Embedding:     |   - SentenceTransformer encode(pregunta)  <50ms
|                    |     modelo: paraphrase-multilingual-MiniLM-L12-v2 (384 dim)
|                    |     MULTILINGUE: ES/EN/PT/FR/... (no usa all-MiniLM-L6-v2)
|                    |
| (c) Retrieval:     |   - ChromaDB query top_k_raw=15 (3x top_k final)
|                    |   - Lee /data/vector_store/chroma.sqlite3
|                    |   - Calcula similitud coseno  <50ms
|                    |   - Distancias tipicas: [0.25, 0.30, 0.35, 0.38, 0.42, ...]
|                    |
| (d) Re-ranking:    |   - Si la query tiene keywords (>=4 letras, no stopword):
|                    |     * Para cada chunk: cuenta matches de keywords en
|                    |       `meta["documento"]` (case-insensitive, substring)
|                    |     * boost = matches * 0.07 (descuento de distancia)
|                    |     * d_boosted = max(0.0, d_orig - boost)
|                    |   - Ordena por d_boosted ascendente, top_k_final=5
|                    |   - Si la query NO tiene keywords: top-5 por d_orig
|                    |
| (e) Filtro UMBRAL: |   - Mantiene los que pasan UMBRAL_DISTANCIA_COSENO=0.35
|                    |   - USA d_boosted (no d_orig) para consistencia con re-ranking
|                    |     Si el sistema cree que el chunk es relevante por
|                    |     keywords, no debe descartarlo por su distancia coseno.
|                    |   - Tipicamente 4-5 de 5 chunks pasan
|                    |   - Recorta cada chunk a MAX_CHARS_POR_FRAGMENTO=700
|                    |     (conserva cabecera+final, descarta el medio si >700)
|                    |
| (f) Generacion:    |   - Llama a Ollama HTTP POST /api/generate
|                    |   - num_predict=1024, temperature=0.2
|                    |   - PROMPT v2 con 8 reglas obligatorias:
|                    |     1) USA TODAS las fuentes relevantes
|                    |     2) NO inventes informacion
|                    |     3) CADA bullet con cita (Documento, Articulo X°)
|                    |     4) Lista vertical, un elemento por linea
|                    |     5) Si enumera derechos/deberes, TODOS uno por uno
|                    |     6) NO "Introduccion breve" ni prologos
|                    |     7) NO atribuir articulos al documento equivocado
|                    |     8) NO incluir "Fuentes:" al final (lo agrega el frontend)
|                    |   - TIMEOUT: 40s por intento (TIMEOUT_RESPUESTA=40)
|                    |   - Retry policy: 3 intentos solo en HTTP 5xx
|                    |     (backoff 0/0/2s). FutTimeout NO se reintenta.
|                    |
| (g) Post-proceso:  |   - Bullet `•` (U+2022) -> `- ` (markdown estandar)
|                    |   - Elimina meta-frases del LLM:
|                    |     "(El corpus no contiene...", "No hay informacion...",
|                    |      "No se encontro informacion...", "El fragmento
|                    |      no menciona..."

POR QUE SE BLOQUEABA ANTES (M06 con 30s o 47s):

  1. PROMPT ENORME
     5 chunks x ~2000 chars = ~10000 chars = ~2500 tokens de contexto
     + 800 tokens de prompt + 768 tokens de respuesta
     = 4000+ tokens -> n_ctx=4096 -> muy justo

  2. OFFLOAD GPU<->CPU
     "offloaded 30/33 layers to GPU"
     3 capas quedan en CPU, se intercambian con cada inferencia
     Picos de 20-40s en lugar de 5-10s

  3. LOOP INTERNO DEL LLM
     Si el prompt esta en el limite, el modelo puede entrar en loop
     generando el mismo token repetido -> no termina nunca
     Ollama devuelve HTTP 500 despues de 15s de timeout interno

  4. SIN BACKOFF EN RETRY
     Antes: 2 intentos sin espera -> si Ollama estaba sobrecargado,
     ambos intentos fallaban rapidamente -> M06

  5. MODELO DE EMBEDDINGS EN INGLES (chromadb 1.x)
     El vector store se creo con `all-MiniLM-L6-v2` (ingles) y el
     fallback `query_texts=` lo usaba para queries en espanol
     -> distancias altas, chunks irrelevantes -> M04 o M02 baja calidad


CONFIGURACION ACTUAL (ver config.py y rag_pipeline.py):

  - UMBRAL 0.32 -> 0.35: captura el chunk correcto sin tanto ruido
  - TIMEOUT 15s -> 40s: holgura para Llama 3 8B con offload CPU
  - MAX_CHARS 1200 -> 700: input ~42% menor, evita n_ctx=4096
  - num_predict 768 -> 1024: cabe 20+ viñetas, suficiente para enumeraciones
  - 3 reintentos con backoff 0/0/2s: tolera HTTP 500 transitorio
  - FutTimeout NO se reintenta: el modelo es lento, retry solo acumula tiempo
  - PROMPT v2 con regla #1 "USA TODAS las fuentes": evita respuestas cortas
    que ignoraban el Estatuto cuando había un chunk más breve
  - Modelo multilingüe (paraphrase-multilingual-MiniLM-L12-v2) con
    query_embeddings= (no query_texts=) para queries en español
  - top_k_raw=15 (3x top_k final): da margen al re-ranking para encontrar
    chunks relevantes que están más abajo en la lista por distancia coseno
    pero ganan por match de keywords con el nombre del documento
  - Re-ranking híbrido: boost = 0.07 por keyword de la query presente en el
    nombre del documento. d_boosted se usa para ranking Y filtro UMBRAL
    (consistencia: si el sistema cree que es relevante por keywords, no
    debe descartarlo por su distancia coseno).
  - Post-proceso: `•` -> `- ` (markdown) y eliminación de meta-frases del LLM


EL FRONTEND NO BLOQUEA EL SISTEMA:
  - Solo deshabilita el boton "Enviar" mientras `cargando=true`
  - Si quieres cancelar, solo cierra la pestana o navega
  - El backend tiene 3 reintentos maximos para HTTP 5xx
  - En timeout, devuelve M06 inmediatamente (sin reintento)


EL BACKEND SI BLOQUEA EL REQUEST HTTP:
  - uvicorn es sync (no async)
  - El handler espera la respuesta del LLM
  - Si el LLM tarda, el request HTTP espera
  - Frontend muestra spinner hasta respuesta o error

  - docker logs oe5-backend --tail 50: ultimas 50 lineas
  - GET /salud: healthcheck simple (modo_piloto + status)
  - GET /config-publica: parametros vigentes del backend
  - GET /documentos: introspeccion del corpus indexado
